# Feature spec: Moodboards — Pinterest import, and a right-click clipper

**Status: proposed, not built.** Extends
[`09-moodboards.md`](09-moodboards.md), which is itself unbuilt and unanswered.
Same rule as its parent and as spec 8: **nothing here is built, schema
included, until §12 has answers** — and this one has a hard external
dependency on top of that (§4: a Pinterest developer app only the planner can
register).

**Depends on:** spec 9, entirely. Every table, the bucket, the upload
pipeline, the sharing model and the privacy posture come from there; this
adds two ways for an image to arrive that are not "the planner picked a file".

**Where this came from:** a technical spec the planner supplied, written for
a standalone prototype — Express, socket.io, SQLite, an unauthenticated
`POST /api/clip`, a hardcoded Pinterest token, an HTML5 canvas with x/y
coordinates. §1 is an honest accounting of which parts of that survive
contact with this codebase and which fight it, because a straight
implementation of it would mean a second server, a second datastore and a
second auth model sitting next to the ones this app already has.

---

## 1. The supplied spec, translated

| Supplied | Verdict | What it becomes here |
| --- | --- | --- |
| Node.js / Express server | **Replaced** | A Next.js route handler, `POST /api/clip`. This app already has `/api/cron/*`, `/api/export/*` and `/api/qr/*`; a second HTTP server would need its own host, its own deploy and its own copy of the auth and tenancy rules. |
| socket.io / SSE, a long-lived WebSocket | **Replaced** | Supabase Realtime (§7). Not a preference — Vercel's serverless functions have no process that outlives a request, so there is nothing for a socket to stay open against. Supabase is already paid for, already holds the row being inserted, and `src/lib/supabase/browser.ts` says in its own comment that realtime is the reason it exists beyond auth. |
| SQLite / Lowdb / a JSON file | **Replaced** | Postgres, with `wedding_id`, like everything else. A second datastore is a second source of truth and an instant violation of `docs/HANDOFF.md` §5 rule 1. |
| `PINTEREST_ACCESS_TOKEN` in `.env` | **Replaced** | An OAuth connection stored per wedding and refreshed (§4). Not pedantry: Pinterest's v5 access tokens are short-lived and come with a refresh token, so a static env var works for an afternoon and then silently stops. |
| OAuth 2.0, scopes `boards:read`, `pins:read` | **Adopted** | Plus the `_secret` variants if secret boards are in scope (§12.2). |
| `GET /v5/boards`, `GET /v5/boards/{id}/pins` | **Adopted** | `/moodboards/[id]/import` (§8). Paginated by cursor, not by page number. |
| Unauthenticated `POST /api/clip` | **Rejected** (§3) | The same endpoint, carrying a clip token. An open endpoint that writes a row *and* pulls a remote URL into your storage bucket is three separate problems at once. |
| Payload `{imageUrl, sourceUrl, title, boardId}` | **Adopted, near enough** | Same shape, plus the token; `boardId` is validated against the wedding, never trusted. |
| HTML5 canvas, x/y coordinates, default `(0,0)` | **Deferred, schema provisioned** (§6) | The grid stays the default and the only *shareable* layout. `x`, `y`, `scale`, `z_index` and a `layout` enum land in the schema now so a canvas mode is a screen later, not a migration. |
| Chrome MV3 extension, `contextMenus`, right-click to clip | **Adopted wholesale** (§5) | The best idea in the supplied spec, and the one this app cannot produce any other way. |
| `activeTab` permission | **Dropped, replaced with something better** | `contexts: ["image"]` already hands the background worker `info.srcUrl` and `info.pageUrl` with no host access at all. What is actually wanted on Pinterest is a *content script*, which is a narrower and more useful thing (§5). |

**The short version: the two features are right and the plumbing is wrong for
this codebase.** Importing a Pinterest board and right-clicking an image into
a board are both genuinely valuable and neither needs a new server, a new
database or a new auth model.

## 2. Scope

**In:**

- **Pinterest import.** Connect an account once, browse your own boards, pick
  one, preview its pins, tick the ones you want, import them into a moodboard
  as ordinary items with `source_url` and `credit` filled in from the pin.
  Re-importing the same board skips what is already there.
- **A Chrome extension (MV3)**: right-click any image on any site →
  "Send to moodboard →" → a submenu of your boards. Includes a Pinterest
  content script that resolves the *pin* URL and the largest available image
  rather than the thumbnail the grid happened to render.
- **Clip tokens**: one per browser/device, created in `/settings`, labelled,
  revocable, `last_used_at` visible — so "revoke my laptop" is a button.
- **A live board.** An open `/moodboards/[id]` tab shows a clipped image
  within a second or two, with no refresh.
- **One hardened image fetcher** used by both paths (§3), because both end in
  "the server has a URL that someone else chose".

**Out:**

- **No Chrome Web Store listing.** Loaded unpacked, in developer mode, on two
  laptops. A store listing means a review, a privacy policy and a public
  identity for a tool with two users.
- **No Firefox or Safari build.** MV3 differs enough in both to be a separate
  piece of work, and neither is what the planner uses.
- **No Pinterest writes.** No creating pins, no following, no boards created
  on Pinterest. `boards:read` and `pins:read`, and nothing that could modify
  somebody's account.
- **No scraping.** If the API cannot reach it, it does not get imported. No
  HTML parsing of pinterest.com, no headless browser, no logged-in session
  replay — all three break, all three are against the terms, and all three
  are the reason the official API exists.
- **No canvas layout screen in this pass** — columns only (§6).
- **No auto-publishing.** An imported or clipped image lands in a board; if
  that board already has a live public share, §11 warns rather than silently
  putting somebody else's photograph on a public URL.

## 3. `POST /api/clip`, and the two things it must not become

The supplied spec's endpoint takes a JSON body with an image URL and saves it.
Unauthenticated, that endpoint is:

1. **An open write** into a private database and a metered storage bucket.
2. **An SSRF proxy.** "Here is a URL, go and fetch it from your server" is the
   textbook shape. From inside a hosting provider's network that can mean
   cloud metadata endpoints, internal services, and anything else reachable
   from the function that a browser could not reach directly.

Both are fixable, and neither is fixable by obscurity.

### 3a. The credential

A new table, `moodboard_clip_tokens`. 32 random bytes from
`generateInviteToken()`, stored as `hashInviteToken()` — the same machinery,
the same pepper, the same reasoning as spec 9 §5 and V1's invitations. The
extension holds the raw token in `chrome.storage.local` and sends it as
`Authorization: Bearer <token>`, which is the pattern
`/api/cron/reminders` already uses for `CRON_SECRET`.

The token resolves to exactly one `wedding_id`. Every subsequent query is
constrained to it, and `boardId` from the payload is checked against it before
anything is written — the same rule `src/server/rsvp/resolve.ts` states for
invitation tokens, for the same reason: this runs as the service role, so RLS
is not the thing protecting it.

Failures throttle through `rsvp_token_attempts` (spec 9 §5 already reuses it;
it holds an IP hash, a flag and a timestamp, and deliberately no wedding and
no token, so it needs no schema change to count a third kind of failure).

### 3b. The fetcher

One module, `src/lib/net/fetch-image.ts`, used by the clip endpoint, the
import path and nothing else. Rules, all of them non-optional:

- **`https:` only.** No `http:`, no `file:`, no `data:`, no `blob:`.
- **The connected address is checked, not the hostname.** Rejecting
  `localhost` and `127.0.0.1` by string is not a control; `evil.example.com`
  resolving to `169.254.169.254` is the actual attack. The check runs against
  the resolved address at connect time — an `undici` `Agent` with a `connect`
  hook, because Node's global `fetch` gives no other seam — and rejects
  loopback, link-local, every RFC1918 range, CGNAT (`100.64.0.0/10`), IPv6
  unique-local and IPv4-mapped IPv6. Checking at connect time rather than with
  a pre-flight DNS lookup is what closes the rebinding gap between the two.
- **At most two redirects**, each re-validated the same way.
- **Content type from the response**, not from the URL's extension, and it
  must be one of spec 9 §4's accepted types.
- **A hard byte ceiling enforced while streaming** (spec 9's
  `MAX_SOURCE_BYTES`), so a declared `Content-Length` is never trusted, and a
  10-second timeout.
- **No credentials, no cookies, no `Authorization` forwarded outbound.**

This is the honest answer to spec 9 §12.3, which asked whether the server
should ever fetch a URL and recommended "not this pass". The clipper forces
the question, so it gets answered properly rather than avoided — and the
answer is a single audited module with one job, not an ad-hoc `fetch()` in
two route handlers.

### 3c. Who resizes the pixels

Spec 9 §4 keeps image processing in the browser and out of the server, on
purpose. Clipping and importing both break that, because there is no browser
holding the file. Rather than adding `sharp` to a Vercel function, the work
moves back to a browser in both cases:

- **Clipping:** the extension downscales before it POSTs. MV3 service workers
  have no DOM, so this runs in an **offscreen document** (`reason: "DOM_PARSER"`
  / `"BLOBS"`) with a canvas — an ordinary MV3 pattern. The extension sends
  the two derivatives spec 9 already defines, as multipart, and the server
  stores what it is given after re-checking type and size. It never fetches
  the image at all in the normal case; §3b's fetcher is the fallback for when
  the offscreen decode fails (a CORS-restricted image, a format the extension
  cannot decode).
- **Importing:** the *planner's own browser* does it. The server lists the
  pins (it holds the OAuth token), the browser fetches each image, downscales
  on canvas, and uploads through spec 9's existing signed-upload path. Nothing
  new server-side at all.

**One unknown, named rather than assumed:** whether Pinterest's image CDN
sends permissive CORS headers. If it does not, `canvas.toBlob()` on a
cross-origin image throws a `SecurityError` and the browser-side import path
dies. The fallback is `GET /api/proxy-image?...` — same-origin, so the canvas
is not tainted — which streams bytes through §3b's fetcher and **never writes
to storage**. Build the direct path, test it against a real pin early (build
order step 3), and keep the proxy as the documented fallback. Do not assume
either way; this is exactly the kind of thing that works on one CDN path and
not another.

## 4. Pinterest, honestly

**Read this before committing to the import half.** These are the things that
decide whether it is an afternoon or a fortnight, and every one of them is
outside this repository's control:

- **A developer app has to exist**, registered by the planner at Pinterest's
  developer portal. Nobody else can do this step.
- **New apps start with limited/trial access**, which is typically scoped to
  the app owner's own account and data. For a personal tool that is exactly
  what is needed — but it means the connection only ever works for the account
  that owns the app, and "let my partner connect their Pinterest too" may
  require a review that a two-person wedding planner will not get.
- **Access tokens expire** and refresh tokens are issued alongside them. This
  is why §1 replaces the supplied spec's static env var: the token stored at
  connect time stops working weeks later, mid-import, with an error that looks
  like a bug.
- **Redirect URIs generally must be HTTPS**, which makes a plain
  `http://localhost:3000` OAuth callback awkward. Workarounds: run the connect
  flow against the deployed URL, or a tunnel. Worth discovering now rather
  than at step 5.
- **Secret boards need the `_secret` scopes**, and a moodboard-shaped
  Pinterest board is quite often a secret one.
- **Pins are paginated by a cursor/bookmark**, and rate limits apply. A
  400-pin board is several calls and needs a progress bar rather than one
  request.
- **Image URLs come back at several sizes** in the pin's media payload. Take
  the largest offered; do not hand-edit CDN URL paths for the API import (the
  extension does that, as a heuristic with a fallback — §5).

**A caveat on all of the above:** Pinterest's access tiers, scope names and
terms have changed more than once, and this file is written from knowledge
with a cutoff. **Verify each point against the current developer docs before
building**, and treat anything here that disagrees with them as wrong.

**Terms.** The API is the sanctioned route and a personal tool reading the
owner's own boards is what it is for. Rehosting those images into a private
bucket is spec 9 §9's existing posture. Publishing them on a public share is
where care starts, which is why §11 warns before importing into a board that
already has one.

## 5. The extension

Six small files, in `extension/` at the repository root — not under `src/`,
because it is not part of the Next.js build and must never be bundled into it.

```
extension/
  manifest.json      MV3
  background.js      service worker: menus, POSTs, retry queue
  offscreen.html/js  a canvas, for downscaling (§3c)
  content.js         pinterest.com only: better URLs
  options.html/js    paste a clip token, refresh the board list
```

**`manifest.json`:** `manifest_version: 3`; `permissions: ["contextMenus",
"storage", "offscreen", "notifications"]`; `host_permissions` limited to the
app's own origin plus `https://*.pinterest.com/*`; a background
`service_worker`; an `options_page`; an `action` popup showing the last clip
and the current default board.

**Three MV3 traps, named in advance:**

1. **The service worker is killed, often.** Nothing may live in a module-level
   variable between events. State is `chrome.storage.local`, every time.
2. **Context menus do not survive it.** They are created in
   `chrome.runtime.onInstalled` **and** re-created on `chrome.runtime.onStartup`,
   and rebuilt whenever the board list is refreshed. A menu that vanishes
   after a laptop sleeps is the single most likely bug in this file.
3. **A failed clip must not evaporate.** Hotel wifi, an expired token, a
   sleeping Vercel function — the POST fails and the image the planner just
   right-clicked is gone. So a failed clip goes into a retry queue in
   `chrome.storage.local`, the action badge shows the pending count, and
   retries run on the next clip and on startup. A notification says which one
   failed and why.

**The Pinterest content script** is what makes this better than a generic
clipper. Right-clicking a pin in a Pinterest grid gives `info.srcUrl` pointing
at whatever size the grid rendered — often a small thumbnail — and
`info.pageUrl` pointing at the *feed*, not the pin. The content script, on
`contextmenu`, walks up from the clicked element to find the enclosing pin's
`<a href="/pin/…">` for a real `source_url`, and reads the `<img srcset>` for
the largest candidate the page itself offers. It also tries the well-known CDN
size-segment rewrite toward the original, **as a heuristic with a fallback**:
if that URL 404s, fall back to the largest `srcset` entry, then to
`info.srcUrl`. Never fail a clip because the optimistic URL did not exist.

**Board targeting.** `GET /api/clip/boards` returns the wedding's boards for a
clip token; the extension caches them and builds one submenu item per board,
plus "Default board" at the top. Changing the default is one click in the
popup. This is the supplied spec's "active mood board", made explicit rather
than implicit — a hidden global "active board" is how an image ends up in the
wrong one and nobody notices for a week.

**Installation** is a paragraph in `extension/README.md`: clone, enable
developer mode, "Load unpacked", paste a clip token from `/settings`. No store,
no signing, no review.

## 6. Canvas versus grid

The supplied spec wants a canvas with per-image coordinates. Spec 9 specifies
a masonry grid ordered by `sort_order`. These are different products, and the
difference matters most where the feature is actually used:

- A **freeform canvas** — drag anywhere, overlap, scale, rotate — is better
  for arranging a vibe, and is a substantially larger build: pan, zoom, hit
  testing, z-order, snapping, and a touch story. `docs/wedding-platform-spec.md`
  already has the standing guidance for when this app does build one, for
  seating: SVG with pointer events, not dnd-kit.
- A **grid** is what works on the phone where every guest and most vendors
  will open the share link, and it needs no viewport state to be shareable.

**The proposal: both, eventually; grid first, and the schema pays for the
option now.** `moodboards.layout` (`grid` | `canvas`, default `grid`) and
nullable `x`, `y`, `scale`, `z_index` on `moodboard_items` ship in the same
migration. Nothing reads them in this pass. A canvas mode later is then a
screen and a save action, not a migration on a table that by then has content
in it. The cost of provisioning now is five nullable columns; the cost of not
doing it is `0014_moodboard_canvas.sql` and a backfill.

**The shareable surfaces stay grid either way** (§12.5). A public board that
requires panning is a public board people close.

## 7. Live updates

**Supabase Realtime, used as a nudge rather than as a data channel.**

`/moodboards/[id]` subscribes with the browser client and the planner's own
session — so RLS applies to the subscription, which is the entire reason this
is acceptable where a socket carrying image data would not be — to
`postgres_changes` on `moodboard_items`, filtered to that board. On an insert,
the page calls `router.refresh()`.

It refreshes rather than rendering the payload directly because **the new row
is not renderable on its own**: spec 9's bucket is private, so an image needs
a signed URL, and signing is a server capability the browser does not and
should not have. `router.refresh()` re-renders on the server, which signs. The
realtime event carries no image data and needs to carry none.

**The migration trap:** adding a table to Supabase's realtime publication is
`alter publication supabase_realtime add table …`, and that publication does
not exist on the bare PostgreSQL cluster `scripts/verify-migrations.sh` builds
— it is created by Supabase, exactly like `storage.objects` in spec 9 §3. So
the statement is **guarded**:

```sql
do $$
begin
  if exists (select 1 from pg_publication where pubname = 'supabase_realtime') then
    alter publication supabase_realtime add table public.moodboard_items;
  end if;
end;
$$;
```

A no-op on the test cluster, correct on a real project, and `verify-migrations.sh`
stays untouched. Same shape of problem, same shape of answer.

**The fallback, if browser-side realtime turns out to be fiddly:** the board
page polls a tiny route for `max(updated_at)` every few seconds while the tab
is visible, and calls the same `router.refresh()`. The action is identical
either way, so the fallback is a few lines and no redesign. Do not build both.

## 8. Schema delta

On top of spec 9's three tables:

```
pinterest_accounts        id, wedding_id, external_user_id, username,
                          access_token_encrypted, refresh_token_encrypted,
                          token_expires_at, scopes (text[]),
                          connected_by (auth.users, on delete set null),
                          created_at, updated_at
                          unique (wedding_id)          -- one connection per wedding

moodboard_clip_tokens     id, wedding_id, label, token_hash (unique),
                          token_encrypted, default_moodboard_id (nullable),
                          last_used_at, revoked_at,
                          created_by (auth.users, on delete set null),
                          created_at
                          unique (id, wedding_id)

moodboard_items         + origin (moodboard_item_origin, default 'upload')
                        + external_id (nullable)      -- the pin id
                        + x, y, scale, z_index        -- all nullable, §6
                        + unique (moodboard_id, external_id) where external_id is not null

moodboards              + layout (moodboard_layout, default 'grid')
```

- **`moodboard_item_origin`**: `upload` | `clip` | `pinterest`. Worth a column
  rather than an inference from `source_url`: it drives what the item panel
  shows, and "where did all these come from" is a question the planner will
  ask of a board with 90 items in it.
- **`external_id` + that partial unique index is the whole dedupe story.**
  Re-importing a board skips pins already present, so import is idempotent and
  needs no run log, no diffing UI and no "are you sure" — import twice, get
  the new ones.
- **Tokens are encrypted, not hashed**, in `pinterest_accounts`: they have to
  be *used*, not merely compared. `src/lib/tokens.ts` already has AES-GCM
  `encryptToken`/`decryptToken` under a key derived from the pepper, which is
  the same requirement V1 had for recovering invitation links. `decryptToken`
  returning null after a pepper rotation means "reconnect Pinterest", which is
  a sentence the settings screen should be prepared to say.
- **Clip tokens are hashed** (compared, never used), matching invitations.
- Tenancy as ever: `wedding_id`, `unique (id, wedding_id)`, composite FKs, and
  both new tables into `0002`'s `tenant_tables` array.

**Migration: `0014_moodboard_clipper.sql`**, on top of spec 9's `0013`. Also
carries the guarded realtime publication statement from §7.

**`.env.example`:** `PINTEREST_APP_ID`, `PINTEREST_APP_SECRET`, both server
only, both optional — the app must boot and every non-Pinterest feature must
work with them unset, which is the same treatment `RESEND_API_KEY` gets.

## 9. Routes and screens delta

| Route | What it does |
| --- | --- |
| `POST /api/clip` | Bearer clip token → one wedding. Accepts multipart (two derivatives from the extension, §3c) or JSON (URL only, server fetches via §3b). Validates board, type, size and caps, writes the item, returns its id. |
| `GET /api/clip/boards` | Same auth. The wedding's boards, for the extension's submenu. |
| `GET /api/proxy-image` | Signed-in collaborator only. The CORS fallback from §3c. Streams bytes, writes nothing, never reads a URL that did not come from a pin the caller is importing. |
| `/api/pinterest/callback` | OAuth redirect target. Exchanges the code, stores the encrypted tokens, redirects to `/settings`. |
| `/moodboards/[id]/import` | Pick a Pinterest board, see its pins as a grid of checkboxes with the already-imported ones ticked and disabled, select, import with a progress bar and a per-pin failure list. |
| `/moodboards/[id]` | Two additions: an "Import from Pinterest" button, and the realtime subscription from §7. |
| `/settings` | A "Pinterest" card (connect, connected-as, disconnect, reconnect-needed state) and a "Clip tokens" card (create with a label, copy once, last used, revoke). |

## 10. Test plan delta

On top of spec 9 §10:

- **Unit** — `src/lib/net/is-private-address.ts`: every range in §3b, IPv4,
  IPv6, IPv4-mapped IPv6, and the boundaries of each CIDR. This is the test
  that matters most in the whole feature; a hole here is a hole in a server
  that fetches URLs strangers can influence. Also `src/lib/pinterest.ts`:
  picking the largest image from a media payload, cursor pagination
  accumulation, and mapping a pin to item fields.
- **SQL** (`06_moodboard_clipper.sql`): cross-wedding RLS on both new tables;
  a clip token in wedding A refusing to resolve a board in wedding B;
  `token_hash` uniqueness; the `(moodboard_id, external_id)` partial unique
  index refusing a duplicate import and permitting many nulls; one
  `pinterest_accounts` row per wedding.
- **Endpoint tests, written as unit tests against the handler**: no token →
  401; revoked token → 401; valid token, other wedding's board → 404, *not*
  403 (a 403 confirms the board exists); oversized body → 413; a
  `Content-Type` of `text/html` on a fetched URL → rejected; a URL resolving
  to `127.0.0.1`, to `169.254.169.254`, and to a public address that redirects
  to one → all three rejected.
- **Extension**, by hand, because there is no harness for it: clip from
  Pinterest, from Instagram, from a plain blog, from a `data:` image (rejected
  cleanly), with the laptop offline (queued, badge, retried), with a revoked
  token (a notification that says so). Confirm the menu still exists after
  the machine sleeps and after a browser restart — §5's trap 2.
- **Live pass:** two browser windows on the same board, clip from one, watch
  it appear in the other without a refresh. Then the same with an import.
- **Pinterest pass**, which cannot be faked: connect a real account, import a
  real board of 100+ pins, confirm pagination and the progress bar, re-import
  and confirm every pin is skipped, disconnect and confirm the boards list
  disappears without touching any imported item.

## 11. Build order

1. **§12 answered, and a Pinterest developer app registered** (§4). Steps 6–8
   cannot start without it; 2–5 can.
2. `0014_moodboard_clipper.sql` + `src/lib/types/database.ts`.
3. **`src/lib/net/` first, with its tests** — the address checks and the
   fetcher, before anything calls them. Also settle the CORS question from
   §3c here with one real pin URL, because the answer decides whether the
   import needs the proxy route.
4. `POST /api/clip` + `GET /api/clip/boards` + clip tokens in `/settings`.
   Prove it with `curl` before an extension exists.
5. The extension: manifest, menus, options, offscreen downscale, retry queue,
   Pinterest content script. Then §7's realtime subscription, so the clip
   lands live.
6. `src/lib/pinterest.ts` + the OAuth connect/callback/refresh + the settings
   card.
7. `/moodboards/[id]/import`.
8. Seed data, `06_moodboard_clipper.sql`, `extension/README.md`, the
   `.env.example` lines, full check pass, then §10's manual passes.

**Steps 2–5 are a complete feature without Pinterest at all** — right-click
any image anywhere on the web into a board, live. If Pinterest's developer
access turns out to be slow or restricted (§4), that half can wait
indefinitely without stranding anything, and the clipper is arguably the more
useful half anyway: it works on Instagram, on a florist's site, and on a
photographer's portfolio, none of which the Pinterest API can see.

## 12. Open questions

1. **Is there a Pinterest developer app, or will you register one?** Nobody
   else can. Recommendation: register it early and check what access tier it
   lands in (§4) — the answer decides whether steps 6–7 are an afternoon or
   are blocked on a review.
2. **Do secret boards matter?** If the moodboard-ish board is secret, the
   `_secret` scopes are needed. Recommendation: request them.
3. **Clip authentication: a per-device token (§3a)?** Recommendation: yes.
   The alternative — relying on the signed-in cookie — means the extension
   only works while a session is live, breaks on cookie policy changes, and
   cannot be revoked per device.
4. **Realtime, or polling (§7)?** Recommendation: realtime, falling back to
   polling only if it fights. Both end in `router.refresh()`.
5. **Canvas: columns now, screen later (§6)?** Recommendation: yes — and
   shareable surfaces stay grid permanently, because they are opened on
   phones. Say so now if a freeform canvas is the thing you actually want,
   because it changes the size of spec 9 as well as this one.
6. **Should the clipper work everywhere, or only on Pinterest?**
   Recommendation: everywhere, with Pinterest-specific smarts (§5). The
   restriction would buy nothing.
7. **What happens when you import into a board that already has a live public
   share?** Recommendation: warn before importing, and never auto-publish.
   Rehosting somebody else's photographs privately and publishing them are
   different acts (spec 9 §9).
8. **Server-side fetching is now in scope (§3b)** — this reverses spec 9
   §12.3's recommendation, because the clipper cannot work without it.
   Recommendation: confirm, on the condition that it lives in exactly one
   audited module with the address checks unit-tested.
9. **`extension/` in this repository, or its own?** Recommendation: this one.
   It is versioned against an endpoint in this app and would drift apart
   immediately anywhere else. It is excluded from the Next.js build and from
   `tsconfig`.
