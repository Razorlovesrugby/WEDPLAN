# Feature spec: Budget — quantity × unit price, and linking to an existing task

**Status: proposed, not yet built.** Two small, independent additions to
spec 6 (budget management), which is itself already built
(`docs/HANDOFF.md`, session 12). Part A needs the planner's answers to the
open questions in section 4 before anything beyond schema is built — same
rule every spec in this directory follows. Part B needs no new decision at
all; see section 5.

**Depends on:** Spec 6, already built. Nothing else.

## 1. What this changes

**Part A — a manual quantity × unit price costing option.** Spec 6 already
has "per unit" costing (`per_adult` / `per_child` / `per_seat`), but every
one of those multiplies by a *live guest count* — there's no way to price a
line by any other countable thing. Plenty of real wedding costs aren't
guest-shaped: "12 centrepieces @ £25", "3 hire vans @ £180", "40 metres of
fairy lights @ £1.20/m". Right now the only way to capture one of those is
a flat line where the planner does the multiplication by hand and re-types
the total every time the quantity or the price changes. This adds a fifth
basis where the planner types the quantity directly and the app does the
multiplication — live, the same way `per_adult` already recomputes when the
guest count moves.

**Part B — searching for and linking an existing task**, not just a whole
list or a brand-new one. Spec 6, section 7 already specifies this exactly:
*"a 'Link a list…' / 'Link a task…' combobox... plus the inline-create
shortcut."* Session 12's build shipped the list search and the "+ Create a
new task and link it here" shortcut, but never built the "Link a task…"
search over tasks that already exist. This is a gap against something
already approved, not a new ask.

## 2. Scope

**In:**
- New `quantity_basis` value for a manually-counted item (exact name is an
  open question, section 4). It reuses the existing `unit_price` column
  (already on `budget_items`, already shared by every per-unit basis) and
  adds one new column, `quantity`, entered directly by the planner.
- `computed_current` for this basis is `quantity × unit_price`, live —
  same as every other per-unit basis, so editing either number updates the
  line's current total immediately, with no separate save step.
- The item editor's basis picker gains this as a fifth option; selecting it
  shows a quantity field next to unit price, instead of quantity coming
  from guest counts.
- `/budget`'s "Linked" popup gains a second search box, "Link a task…",
  searching every task in every list (not scoped to one list), excluding
  tasks already linked to this line — same type-to-filter/click-to-link
  interaction the existing "Link a list…" box already uses.

**Out:**
- No change to `per_adult` / `per_child` / `per_seat` / `consumption` —
  none of those start reading from the new `quantity` column; they keep
  deriving their count from guests exactly as spec 6 built them.
- No unit-of-measure field ("metres", "vans", "days"). The label already
  carries that ("40 metres of fairy lights") — a dedicated unit field is a
  reasonable later refinement if it turns out to matter, not built now.
- No change to how a whole list is linked, or to the "+ Create a new task"
  shortcut — both already work as spec 6 built them.

## 3. Data model

```
budget_items   quantity_basis gains a new enum value (name: open question 1)
               quantity  numeric, nullable — set only when quantity_basis
                         is the new value; unused (null) for every other basis,
                         same "nullable, meaningful only for its own basis"
                         convention unit_price already follows.
```

- No new table. One enum value, one column, on the migration that follows
  `0010_budget.sql` in sequence (spec 5's `0008`/`0009` may land first or
  after — see `docs/HANDOFF.md`'s note on migration numbering; this one
  just needs to come after `0010`).
- `v_budget_items`'s `computed_current` CASE gains one branch:
  `quantity * unit_price`, rounded the same way the existing per-unit
  branches already are.
- `src/lib/budget.ts`'s `computeCurrent` gains the matching case, mirrored
  and unit-tested exactly like every other basis already is — same
  "duplicate the view's logic, test against the SQL suite" pattern
  `tier.ts` established and spec 6 already follows throughout.

## 4. Open questions (Part A)

1. **What is the new basis actually called?** In the schema enum and in the
   picker's label. Candidates: `manual`, `quantity`, `unit_count`, `count`.
   Cosmetic, but worth deciding once.
2. **Whole numbers only, or decimals?** "3 vans" is a whole number; "40.5
   metres" or "2.5 hours of DJ time" isn't. Decides the column's type and
   the input's validation.
3. **Does `quantity` get a default** (e.g. defaults to 1, so a planner who
   forgets to set it still gets a real total rather than zero), or must it
   be entered with no default and an empty value blocks saving?
4. **Does this basis count toward the wedding-level per-head figures** on
   `/guests/rank` and `/budget` (`v_budget_summary.per_head_adult` /
   `per_head_seat`, which today sum every line where `quantity_basis <>
   'flat'`)? A "12 centrepieces" line isn't really a per-guest cost even
   though it has a quantity — this spec assumes **no**, the new basis is
   excluded from that sum, but the planner may see it differently, and
   spec 6 section 2 defines that figure broadly enough ("every per-unit and
   consumption line") that it's worth confirming rather than assuming.

## 5. Part B — closing the existing-task-linking gap

No open question here: spec 6, section 7 already decided this shape. What's
missing is purely a build gap from session 12. Once the planner says to
proceed (on this spec, or on Part B alone), it's:

- `src/server/queries/budget-links.ts`: a new query searching `list_items`
  across every active list for the current wedding, excluding ids already
  present in that budget line's `v_budget_item_tasks` rows.
- `src/components/budget/budget-links-popup.tsx`: a second search box next
  to "Link a list…", reusing `linkBudgetItemToTask` (already built) on
  selection — no new server action needed, since the action side of this
  was already built and only the search UI was missing.

## 6. Test plan

- Unit: `src/lib/budget.test.ts` gains cases for the new basis —
  quantity × unit_price, a zero quantity, and (once open question 2 is
  answered) either an integer-only or a fractional-quantity case.
- SQL: `supabase/tests/03_budget.sql` gains an assertion for the new
  `computed_current` branch, same pattern as the existing five-basis
  coverage.
- Browser pass: add a quantity-basis item, confirm the live total updates
  as either number changes with no page refresh; search for and link an
  existing task from the popup, confirm it appears marked "linked
  individually" and the reverse badge shows up on `/lists/[id]` and
  `/timeline`.
